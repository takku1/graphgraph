# GraphGraph 0.1.0 — The Path to 10/10

**Date:** 2026-07-24
**Method:** Gray-box, two evaluation cycles. CLI only; source and git history never read.
Ground truth derived by reading the target repos. All numbers below are measured on frozen
control fixtures (`requests` py, `express` js, `ripgrep` rs, `sympy` py 40k-node, `flask` doc-heavy).
**Purpose:** Not a findings dump — a prescriptive roadmap. Every requirement below is stated as a
**falsifiable acceptance gate** with a measured *current* value and a computed *floor*.

---

## Where we are

**Today: 6.5/10** (up from 6.0 — two plumbing bugs fixed between cycles). **Ceiling: 9.5–10.**

Recent progress (cycle-over-cycle, verified):
- `--max-nodes` now honors its value and is monotone across all repos — **was the #1 finding, now FIXED.**
- The universal false staleness warning ("stale for 0 changed and 0 deleted") is **gone.**
- No regressions: `update` size-invariance still 0.96×; Python recall still 6/6.

The remaining distance to 10 is **not** architecture. The hard, expensive problem — incremental
size-invariant updates — is already solved and at the floor. What separates 6.5 from 10 is four
things, in strict priority order:

1. **Ranking / anchor selection** (caps everything downstream)
2. **JavaScript extraction** (caps retrieval on a whole language)
3. **Quality signals that actually vary** (so an agent can trust or reject a packet)
4. **The process boundary** (so the already-O(Δ) update loop becomes a fast edit loop)

Everything else is polish. Below, each is a gate.

---

## The scoring model — why the ceiling is layered

You cannot retrieve what was never extracted, and you cannot rank what was never retrieved.
So the score is capped by the *lowest* layer, not the average:

```
extraction  ──caps──▶  retrieval  ──caps──▶  ranking  ──caps──▶  agent trust
   JS 2/10              rust 2/6            MRR 0.007          signals constant
```

A 10/10 requires every layer at ≥9. Weight the roadmap by the cap, not by ease.

## GATE 1 — Ranking: the correct node must be near the top

**This is the single most important gate. It caps the usefulness of every successful retrieval.**

### Measured today
| repo | recall@packet | mean MRR | worst case |
|---|---|---|---|
| requests (py) | 6/6 | 0.604 | acceptable |
| express (js) | 4/6 | 0.472 | — |
| **ripgrep (rs)** | **2/6** | **0.007** | correct node at rank ~76; `ndcg@10 = 0.0` |

Even the *successes* rank badly: `"how are gitignore files parsed"` → recall 1.0, **MRR 0.013**
(answer ~76th in a 107-node / 3308-token packet). A targeted query naming its own answer
(`rebuild_auth`) returned MRR 0.031 (~32nd).

### The critical diagnostic (this cycle)
The `--max-nodes` fix now lets an agent widen context. **I tested whether widening rescues the
misses: raising the budget to 800 nodes recovered 0 of 4 ripgrep misses.** This proves the misses
are **anchor-selection failures, not budget failures** — the relevant `crates/printer` nodes
(417 of them exist, verified via `select`) are never reachable from the chosen anchors at *any*
budget. Ranking/anchoring is the wall.

### Floor
On a graph this size, the correct file for a well-formed NL query should anchor in the top 5.
MRR floor ≈ 0.5–0.8; `ndcg@10 > 0` always when recall = 1.

### Acceptance gates
- `mean MRR ≥ 0.4` on the 6-query ground-truth fixture **for every supported language**
  (today: py 0.604 ✅, js 0.472 ⚠️, rust **0.007 ✗** — ~57× below floor)
- `ndcg@10 > 0` whenever `node_recall = 1` (today: violated on both ripgrep successes)
- Anchor-recall: for each fixture query, the expected file's node must appear in `anchors`
  at default settings (today: fails on 4/6 ripgrep)

### The work
Anchor selection is choosing the wrong seeds and expansion isn't reaching the answer. Likely
levers (inferred, not from source): lexical anchor scoring is under-weighting exact identifier
matches relative to doc/semantic matches; and BFS expansion from anchors terminates before
crossing crate boundaries. Adding qualified-name anchoring (Gate 6) will directly help here —
`rebuild_auth` should anchor a query that contains the word "rebuild auth".

## GATE 2 — JavaScript extraction must reach parity

**Caps retrieval and every graph-derived query on an entire language.**

### Measured today
| language | member-call resolution | `calls_per_symbol` | `select "callers=0"` false-dead-code |
|---|---|---|---|
| Python (sympy) | 33.1% | 1.75 | — |
| Python (requests) | 46.8% | 0.90 | — |
| Rust (ripgrep) | 34.2% | 0.74 | — |
| **JavaScript (express)** | **2.2% (143/6389)** | **0.10** | **2907/3087 nodes (94%)** |

### Root cause (inferred from target source + extraction counts)
Express uses prototype-assignment style: `res.json = function json(obj){…}`. The extractor
classifies these as `function` (2861) not `method` (85); a call `res.json(...)` has receiver `res`
(a parameter), so it lands in `unknown_receiver` (6246 of 6389). Result: `calls` edges essentially
don't form, so dead-code detection reports 94% of the codebase as uncalled.

### Floor
Python/Rust already hit 33–47% with the same machinery; JS should reach the same band once
prototype/object-literal method assignment and `this`/receiver binding are modeled. Target ≥ 30%.

### Acceptance gate
- `calls_per_symbol ≥ 0.5` for every supported-language fixture (today: **js 0.10 ✗**, others pass)
- `select "callers=0"` returns < 40% of source nodes on the express fixture (today: 94%)

### Why this scalar
`calls_per_symbol` (already emitted by `graphgraph profile`) is the nominated **CI gate scalar**:
one number, free to compute, comparable across languages, moves the instant resolution improves.
It cleanly separates the fixtures today (py 1.75/0.90, rust 0.74, **js 0.10**) and would have
caught this regression automatically.

## GATE 3 — At least one quality signal must discriminate good packets from bad

**Without this, an agent cannot trust output and must re-verify everything — which defeats the tool.**

### Measured today (unchanged across both cycles)
- `answerability_status = "answerable"` on **18/18** in-domain queries, including all 6 recall-0 misses.
- Confidence is **inverted**: mean 0.307 for failures vs 0.267 for successes. The two
  highest-confidence queries in the set both failed (0.468 and 0.444, both recall 0).
- GraphGraph's own `eval --calibration` confirms it: `resolution 0.022` vs `uncertainty 0.222`
  (~10% discriminative power), `ece 0.213`, `mce 0.444`; the 0.4–0.6 confidence bin has
  **accuracy 0.0**.
- The control receipt is **constant**: `state=incomplete` on 18/18, gates identical on 17/18
  (`fresh:-,route:-,anchor:+,evidence:-,semantic:+,packet:+`). `next=refresh` on every call would
  drive an agent into an 82s rebuild every single query and still report incomplete.
- `semantic:+` is reported even on sympy, which has **no semantic index at all** (Gate 5).

### Floor
A calibrated confidence has `ece < 0.1` and `resolution > uncertainty/2`. A useful gate is not
constant across a mixed pass/fail set.

### Acceptance gates
- `eval --calibration` reports `resolution > 0.10` and `ece < 0.10` on the mixed fixture
- On a fixture with known passes and failures, `state` and `gates` are **not constant** — they take
  ≥ 2 distinct values correlated with recall
- A gate value that is always `+` or always `-` is treated as a bug, not a signal

### The work
The infrastructure exists — it just doesn't vary. Signals that *are* already computed and *would*
vary: anchor-score margin (top anchor vs second), `matched_anchor_paths / expected_scope`, and the
BFS frontier saturation. Surface one of those as the confidence and calibrate it against the eval
harness that already exists.

## GATE 4 — The edit loop must be fast end to end

**The "whip through calls" property. The expensive half is already done; only the boundary remains.**

### Measured today
| operation | time | note |
|---|---|---|
| `python -c pass` | 86 ms | interpreter floor |
| `graphgraph --version` | 388 ms | **~302 ms pure import overhead** |
| `update` 1 file, 908-node graph | 337 ms | |
| `update` 1 file, **40,571-node graph** | 324 ms | **0.96× — size-invariant, AT THE FLOOR** |
| `query` requests (warm) | 409 ms | ~77% is startup |
| `query` flask **first ever** | **>300 s** | building 22.8 MB semantic index + HF model download |

**~77% of every query's wall time is spent before any graph work begins.** And because `update` is
already O(Δ) and size-invariant, *the process boundary is the only thing between this and a fully
incremental edit loop.* That is an unusually good position: the hard problem is solved.

### Floor
- Startup: lazy-import the embedding stack → ~30 ms for structural/`--version`-class commands (≈10×).
- Query on a resident graph: load-once + anchor + bounded BFS ≈ **5–15 ms** (≈30–90× below today).

### Acceptance gates
- `graphgraph serve` (or equivalent daemon): second query on a resident graph < 50 ms
- Structural commands (`--version`, `ontology`, `frontends`, `select`) < 100 ms cold
  (lazy-load embeddings; today all ~350–400 ms)
- Cold first query on any fixture < 5 s (today: flask **> 300 s**)
- `update` size-invariance stays ≤ 1.5× across a 45× graph-size range (**today 0.96× — protect this**)

### The work
Two independent wins: (a) lazy-import heavy deps off the structural path; (b) a resident-process
mode that keeps the graph loaded. `update` already gives O(Δ) splices — a daemon makes the whole
loop O(Δ). Also precompute `semantic.json` during `scan` (with a progress line) and vendor/pre-fetch
the embedding model so the query path has **no network dependency** (today a first query triggers a
64 MB HuggingFace download with a rate-limit warning).

## GATE 5 — No silent degradation; telemetry must match reality

### Measured today
- **sympy (40,571 nodes) has no `semantic.json`** — some cap skipped it silently, yet queries still
  report `gates=…,semantic:+`. Retrieval quietly drops to lexical/structural at exactly the scale
  where semantics matter most, and nothing tells the caller.
- `semantic.json` is **10–13× the size of the graph** on every repo that built it (requests 9.8×,
  express 13.1×, ripgrep 10.4×, flask 10.3×).
- sympy's `graph.gg.manifest.json` (24.7 MB) is **larger than the graph itself** (18.8 MB).

### Acceptance gates
- If the semantic index is absent or capped, `semantic` gate reports `-` (or a `degraded` state),
  never `+`
- A query that fell back to non-semantic retrieval says so in the receipt
- `semantic.json` size ≤ 3× `graph.gg` (today up to 13×), or is documented as expected

## GATE 6 — Qualified names must be first-class and queryable

### Measured today
The `gg` packet already renders qualified names — `[SessionRedirectMixin::rebuild_auth]` — but they
are not in the `label` field that `select`/`eval` match:

| predicate | matches |
|---|---|
| `label contains SessionRedirectMixin::rebuild_auth` | **0** |
| `label contains rebuild_auth` | 1 |

`requests` has four distinct `send` methods all labelled bare `send`
(`adapters.py:128/634`, `sessions.py:132/752`). An agent cannot ask "who calls `Session.send`" —
the natural form of the question — and eval expectations written naturally (`"Session.send"`)
score 0.0, looking like retrieval failures when they are label-format mismatches.

### Acceptance gates
- `select "label contains Class::method"` resolves qualified names (today: 0 matches)
- Disambiguation: a query about `Session.send` ranks `sessions.py:752` above the three other `send`s
- Expected win: this directly feeds **Gate 1** — qualified-name anchoring should lift MRR

### Why it's high-leverage
The data already exists in the renderer. Exposing it to the query surface is plumbing, and it
attacks the ranking wall (Gate 1) from a second direction for little effort.

## GATE 7 — Advertised surface must all work, docs must not contradict

Low effort, pure correctness — a 10/10 tool has no dead advertised features.

### Measured today
- `--packet hybrid` and `--packet svo` are accepted by the CLI but rejected by the renderer:
  `Error: generated graph packet failed validation: unknown packet format` (2 of 10 formats dead).
- `proxy_tokens` is **not comparable across formats**: `lowlevel` has 2.4× the characters of `gg`
  but reports *fewer* tokens (1072 vs 1359) — inverting the ranking an agent uses to pick the
  cheapest format.
- `--depth` default is documented contradictorily: `scan` help says default **files**, `context`
  help says default **symbols** (still present this cycle).

### Acceptance gates
- Every `--packet` choice renders or is removed from the choice list
- `proxy_tokens` is monotone in real token count across formats (or is replaced by a real tokenizer)
- `--depth` documents one consistent default

## Do NOT touch — already at or near the floor

Regressing any of these would *lower* the score. Protect them with the gates above.

1. **`update` size-invariance (10/10).** 0.96× across a 45× graph-size range, below the process-start
   floor. The hard problem is solved. This is the strongest engineering result in the evaluation.
2. **Self-reported caveats (10/10).** Every `select` auto-appends the precise denominator of its own
   incompleteness (`member-call resolution 2.2% (143/6389)… upper bound, not a proof`). This single
   line is what let me localize the JS failure in one command. Extend this pattern; never remove it.
3. **Honest capability declaration.** `frontends` reports `cpg` as PLANNED / not selectable. No
   phantom features.
4. **`eval` refuses to fake a score** (`null` recall + `scored:false` + a `note`), and the
   **calibration receipt correctly diagnoses its own miscalibration.** Both are exactly right.
5. **`gg` packet design.** Relation legend + numbered nodes + `path:line` + signature + qualified
   name at 3.9 chars/token. It is the right default.
6. **Idempotence** (byte-identical output), **`--anchor-limit`** (monotone, saturating), and the
   two fixes landed this cycle (`--max-nodes`, staleness warning).

## Priority-ordered roadmap to 10/10

| # | Gate | Current → Floor | Effort | Score impact |
|---|---|---|---|---|
| 1 | **Anchor selection + ranking** | MRR 0.007 → 0.5 (rust) | High | **Highest** — caps all retrieval |
| 2 | **JavaScript extraction** | calls/sym 0.10 → 0.5 | High | Unlocks a whole language |
| 3 | **One discriminating quality signal** | resolution 0.022 → 0.10 | Medium | Makes output *trustable* |
| 4 | **Lazy imports + resident process** | 409 ms → <50 ms; 302 ms startup → 30 ms | Medium | The "whip through calls" property |
| 5 | **Qualified names queryable** | 0 → resolves | Low | Feeds #1; disambiguation |
| 6 | **No silent semantic degradation** | `semantic:+` while absent → honest | Low | Telemetry integrity |
| 7 | **Cold-start / offline** | flask >300 s + HF download → <5 s, no network | Medium | First-run usability |
| 8 | **Dead formats + doc contradictions** | 2 dead, 1 contradiction → 0 | Low | Surface correctness |

### The one-line CI gate to adopt first
```
for lang in {py, js, rust}:  assert graphgraph profile → calls_per_symbol ≥ 0.5
```
Free, already computed, and it fails today exactly where the biggest gap is (js 0.10). Pair it with
`mean MRR ≥ 0.4` per language and `eval --calibration → ece < 0.10`, and the three numbers that
gate 10/10 are all things the tool already emits about itself.
